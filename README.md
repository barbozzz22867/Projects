# Практическая работа №1. Определение модели разработки

**Цель:** научиться определять подходящую модель разработки на основе условий проекта.

---

## Задание 1–2. Анализ ситуаций и обоснование выбора

|№|Ситуация|Модель|Обоснование|
|---|---|---|---|
|1|Государственная организация, требования согласованы, изменения только через официальную процедуру, есть подробное ТЗ|Waterfall|Требования стабильны и зафиксированы, изменения строго регламентированы. Каскадная модель даёт понятную последовательность, простой контроль сроков и бюджета, удобную документацию каждого этапа. Риск: позднее обнаружение ошибок в требованиях, заказчик видит продукт только в конце.|
|2|Мобильное приложение, заказчик не знает окончательный интерфейс, после каждой демонстрации предлагает изменения|Agile (или итерационная)|Требования неопределённы и будут уточняться по обратной связи. Гибкий подход позволяет работать короткими циклами, показывать результат и адаптироваться. Риск: без контроля объём работ может расти, нужна постоянная вовлечённость заказчика.|
|3|Интернет-магазин: сначала каталог, затем корзина, оформление заказа, оплата; каждая часть работает самостоятельно|Инкрементальная|Продукт естественно делится на функциональные части, каждая даёт работающий результат. Преимущества: раннее появление работающих частей, удобное распределение работ, приоритизация функций. Риск: нужна продуманная архитектура, сложна интеграция частей.|
|4|Система распознавания документов: простая версия, затем проверка точности, анализ ошибок, многократные улучшения алгоритма|Итерационная|Результат заранее неизвестен, качество достигается за счёт повторных циклов «разработка — проверка — улучшение». Преимущества: ошибки выявляются раньше, продукт постепенно совершенствуется. Риск: возможно увеличение сроков, требуется постоянная оценка результата.|

# Практическая работа №2. Выбор модели для собственного проекта

## 1. Название проекта

**TaskFlow** — система управления задачами для небольших команд

## 2. Краткое описание проекта

Веб-приложение для постановки, распределения и контроля выполнения задач в небольших командах. Руководитель видит статусы задач и загрузку сотрудников, исполнители получают уведомления о дедлайнах.

## 3. Анализ требований

|Вопрос|Ответ|
|---|---|
|Насколько понятны требования заказчика?|Базовые требования понятны (задачи, статусы, дедлайны, отчёты), но детали интерфейса и приоритеты функций требуют уточнения|
|Может ли заказчик менять требования?|Да, вероятны изменения и дополнения по ходу работы|
|Можно ли разделить продукт на отдельные функциональные части?|Да: авторизация, управление задачами, уведомления, отчёты — относительно независимые части|
|Нужно ли регулярно показывать промежуточные результаты?|Да, заказчику важно видеть прогресс и влиять на приоритеты|
|Насколько критичны сроки?|Срок фиксирован — 3 месяца, команда 4 человека, бюджет ограничен|

## 4. Сравнение моделей применительно к проекту TaskFlow

|Модель|Как будет организована разработка?|Преимущества|Недостатки|
|---|---|---|---|
|Waterfall|Последовательно: требования → проектирование → разработка → тестирование → внедрение. Заказчик видит продукт в конце|Понятный план, простой контроль сроков и бюджета, хорошая документация|Изменения требований дороги, заказчик поздно видит результат, ошибки в требованиях всплывут поздно|
|Итерационная|Продукт создаётся циклами: базовый интерфейс → редактирование и статусы → фильтры и поиск. Каждый цикл — оценка и улучшение|Раннее выявление ошибок, учёт обратной связи, продукт постепенно улучшается|Нужна постоянная оценка результата, возможен рост сроков|
|Инкрементальная|Продукт собирается из частей: авторизация → задачи → уведомления → отчёты. Каждая часть работает самостоятельно|Работающие части появляются рано, удобно распределять работу, можно приоритизировать функции|Нужна продуманная архитектура заранее, сложна интеграция частей|
|Agile|Короткие циклы (1–2 недели): планирование → разработка → демонстрация → обратная связь. Приоритеты пересматриваются|Гибкость к изменениям, постоянная вовлечённость заказчика, ранний работающий продукт|Требует дисциплины и вовлечённости заказчика, возможен расползающийся объём работ|

## 5. Выбранная модель

**Agile** (с элементами инкрементальной разработки)

## 6. Обоснование выбора

- **Особенности проекта, повлиявшие на выбор:** требования понятны в основе, но детали будут уточняться; заказчик готов давать обратную связь; продукт хорошо делится на функциональные части; сроки фиксированы (3 месяца), поэтому важна приоритизация.
- **Преимущества подхода:** ранние демонстрации снижают риск «сделали не то»; изменения требований не разрушают план; работающий продукт появляется уже в первые недели; заказчик вовлечён и влияет на приоритеты.
- **Возможные ограничения:** нужна дисциплина команды и регулярная вовлечённость заказчика; есть риск расползания объёма работ — поэтому фиксируем приоритеты и контролируем тройное ограничение (сроки–бюджет–объём).

## 7. Предварительный план разработки (3 рабочих цикла)

|Цикл|Ожидаемый результат|
|---|---|
|Цикл 1 (недели 1–4)|Авторизация пользователей, создание и просмотр задач, база данных|
|Цикл 2 (недели 5–8)|Назначение исполнителей, смена статусов, фильтрация по статусу и исполнителю|
|Цикл 3 (недели 9–12)|Уведомления о приближающихся дедлайнах, отчёт руководителя о загрузке, тестирование и внедрение|

## Ответы на вопросы для представления

**Почему вы не выбрали Waterfall?**
Требования к деталям интерфейса и приоритетам функций будут уточняться, а заказчику важно видеть промежуточные результаты. Waterfall сделал бы изменения дорогими и отложил бы демонстрацию продукта до конца.

**Что будете делать, если заказчик изменит требования?**
Оценим влияние на сроки и объём, согласуем приоритеты в рамках тройного ограничения; изменения войдут в следующий цикл, а менее важные функции могут быть перенесены.

**Можно ли выпустить первую версию раньше?**
Да — уже после первого цикла будет работающая версия с авторизацией и созданием задач; её можно показать заказчику и пользователям.

**Как будете проверять промежуточные результаты?**
Демонстрация в конце каждого цикла, обратная связь заказчика, тестирование функционала цикла, корректировка плана следующего цикла.

**Можно ли совместить итерационную и инкрементальную разработку?**
Да, и это уже заложено: добавляем функциональные части (инкременты), а затем улучшаем их по результатам обратной связи (итерации).
